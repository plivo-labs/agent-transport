agent-transport — the GIL deadlock, before & after

AB-BA deadlock between the Python GIL and the Rust sessions Mutex on the audio_stream + LiveKit (Python) path. Left = shipped 0.1.11 (main, the version crashing prod). Right = 0.2.0 branch (fixed). Python-only — Node has no GIL, so this class can't occur there.

The deadlock, side by side

BEFORE — 0.1.11 (prod) deadlocks
Rust threads invoke stored Python callbacks · send_background_audio holds the GIL
Thread A — Rust tokio WS-handler   Thread B — Python asyncio loop
(no GIL)                           (holds GIL)
caller hangup / Plivo "stop"      BackgroundAudioPlayer(thinking)
  handle_ws                          ep.send_background_audio() ~50fps
  sessions.lock()  ✦ HOLDS          (no allow_threads) ✦ HOLDS GIL
  cleanup_session()                  inner.send_background_audio()
  audio_buf.clear()                  sessions.lock() ⟵ WANTS
  pending_complete()  (Py cb)
  Python::with_gil ⟵ WANTS GIL

   ┌─────────────────────────────────────────┐
   │  A: holds sessions ─ waits GIL           │
   │  B: holds GIL ───── waits sessions       │
   │         ⟲  A B - B A   cycle  ⟲          │
   └─────────────────────────────────────────┘
  ► whole process wedged · SIGTERM useless

Why it locks: the buffer's completion callback was a stored Box<dyn FnOnce> holding a Python closure; firing it from a Rust thread needed the GIL — while the sessions Mutex was held. Meanwhile send_background_audio held the GIL and reached for that same Mutex.

AFTER — 0.2.0 (fixed) cycle broken ×2
Rust emits events over a channel (no Python) · send_background_audio releases the GIL
Thread A — Rust tokio WS-handler   Thread B — Python asyncio loop
(no GIL, never takes it)            (holds GIL)
cleanup_session()                  ep.send_background_audio()
  audio_buf.clear()                  py.allow_threads() ✦ FREES GIL
  event_tx.try_send(Event)           inner.send_background_audio()
  crossbeam — never touches Py      sessions.lock() (GIL already freed)

   A never needs the GIL  ·  B never holds GIL across the lock
   → no shared wait → no cycle can form

events ─► [crossbeam channel] ─► 1 dispatcher thread
            Python::with_gil → sink → loop.call_soon_threadsafe
            (GIL→event_sink order; guard dropped before call)

Why it's safe: Rust threads only push an EndpointEvent onto a crossbeam channel — they never enter Python. One dedicated dispatcher thread drains it and calls the Python sink, which only does loop.call_soon_threadsafe (touches no Rust lock). Either change alone breaks the cycle; both are present.

What changed — and when

FixWhereWhen / bySolves the GIL deadlock?
Event-channel model — Rust threads emit EndpointEvent via try_send instead of invoking stored Python callbacks (removes Thread A's GIL acquisition) events.rs, sip/audio_buffer.rs earlier (committed on 0.2.0) YES — the core fix (both transports)
py.allow_threads on send_background_audio / clear_buffer (removes Thread B holding the GIL across the lock) lib.rs earlier (committed on 0.2.0) YES — the core fix (either alone suffices)
Empirical proof — built the 0.1.11 repro (deadlocks in ~2s, captured native stacks) + a 0.2.0 validation harness recordings/repro_*, validate_* this session verifies, no product code
dispatcher_loop lock order → GIL→event_sink (was holding the sink Mutex across with_gil) lib.rs this session residual AB-BA in the new event-sink path — real, but not the prod-triggering path
wait_for_event — release the event_sink guard before allow_threads (it held the lock while dropping the GIL) lib.rs this session residual AB-BA — would have become active via the dispatcher fix above; now closed
hangup off-loop / fire-and-forget (Plivo REST DELETE spawned on tokio; no Python thread held) plivo.rs, endpoint.rs, LiveKit adapters this session NO — different bug (a loop stall / stutter, not the GIL deadlock)
Honest scope: the GIL crash that hit production was fixed by the earlier work (event model + allow_threads) — this session proved it and closed two latent sibling AB-BAs in the new event-sink machinery (dispatcher_loop, wait_for_event) that the real LiveKit adapter doesn't reach (it sets the sink once and consumes via FfiQueue, never calling poll_event/wait_for_event). The hangup change is a separate responsiveness fix, not a GIL fix.

Empirical result (0.2.0, in-process, Python 3.x): under the same collision that wedges 0.1.11 in ~2s — send_background_audio at 50–100 fps racing 1,246 teardown cycles (cleanup_session under the sessions Mutex) with the dispatcher delivering 4,063 events through a GIL-holding sink — global progress never froze (ops 0→5,281), clean exit. The 0.1.11 wheel, under the equivalent load, deadlocks within seconds (captured lldb stacks: Thread A in take_gil under AudioBuffer::clear; Thread B in Mutex::lock under send_background_audio).
